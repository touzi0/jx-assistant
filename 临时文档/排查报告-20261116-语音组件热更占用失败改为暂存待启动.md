# 排查报告 2026-11-16：语音组件热更「文件被占用」失败 —— 改「占用就暂存、下次启动落地」

> 用户口径（2026-11-16 22:02 转达）：不要做「热更时先杀 worker、换完再拉起来」那套；
> 运行中被占用就标记「待更新」，旧版继续跑、不打断语音输入法，主程序重启时再落地。

## 一、本机 voice 现状（用文件与日志说话）

**结论：现在是完整的 1.3.12，但更新过程中失败过 3 次，每次都以「输入法被杀 + 组件目录被删成半残」收场，最后靠重启时从发布源整装才恢复。**

| 证据 | 内容 |
| --- | --- |
| `组件/voice/manifest.json` | `"version": "1.3.12"`（组件目录内所有文件时间戳统一为 `2026-11-16 13:06:36`＝整装落地，不是半新半旧） |
| `data/updates/state.json` | `"applied": { ..., "voice": "1.3.12" }` |

## 二、根因（改前代码位置）

`update_blocks.go` 的 `applyComponentBlock`（改前 470–536 行）执行顺序是：

1. `a.Bridge.KillComponent(id)` —— 只 `p.Kill()`，**不 `Wait()`**，句柄没释放；语音的输入法也被 onKill 连带 `taskkill /F`；
2. `clearReadonlyTree(dst)` → `os.RemoveAll(dst)` —— **破坏性动作打头**，删到 `voicetype\asr.log` 时（仍被持有）整块失败，前面的文件已经删掉了 → 目录变成半残；
3. 删除失败才 `os.Rename(dst, dst+".old-<ts>")` —— 目录改名要求内部**所有**句柄可删除，同样失败；
4. 于是 `return fmt.Errorf("旧组件目录既删不掉也挪不开…")` → `applyComponentBlocks` 里 `setUpdateError(...)`，用户侧只有设置页一行红字，且**每一轮轮询都重下整个 voice 包**（含模型，数百 MB）再失败一次。

失败后没有任何补偿：输入法被杀后不会自动拉起，语音听写/输入法一直不可用，直到下次重启。

## 三、修复：占用就暂存，下次启动落地

改动文件：

| 文件 | 改动 |
| --- | --- |
| `update_blocks.go`（主体） | 新增 `replaceComponentDir`、`stageComponentBlock`、`ApplyPendingComponentBlocks`、`cleanupComponentAsideDirs`、`errComponentStaged`、`componentBusyReason`、`pendingComponentBlock`；重写 `applyComponentBlock` / `applyComponentBlocks` |
| `update.go` | `UpdateState` 增 `componentsPending`（id→版本），供设置页安静显示 |
| `server.go` | `NewApp` 里 `InitComponents("组件", …)` 之后、`a.Bridge = newBridgeManager(a)` 与 `main` 的 `spawnVoiceType()` **之前**调用 `a.ApplyPendingComponentBlocks()`（启动落地位置） |
| `web/app-settings.js` | 设置·更新分区加一行「组件已下载待启用：voice→x（重启软件后自动生效，不影响当前使用）」 |
| `AGENT.md` | 模块表 `update_blocks.go` 一行同步新机制 |

新行为（按用户口径）：

- **不再杀任何进程**：热更路径彻底去掉 `KillComponent`，语音 worker 与独立输入法照常服务；
- **替换改成「先改名挪开旧目录，再把新目录落位」**：挪不动＝被占用，旧目录分毫未损（不再有「删半残」）；同一个函数在启动落地时复用；
- **挪不动就把包暂存**：下载→sha256 校验→解压→校验 manifest id→落到 `data/updates/pending/<id>`，`state.json` 记 `componentsPending`（版本/file/sha256/暂存目录/时间/中文原因），返回哨兵错误 `errComponentStaged` —— **不写 `LastError`、不广播失败**、旧版继续服务；
- **不重复下载/不重复重试**：下一轮检查发现暂存已是同版直接短路（只取 `releases/latest` + `blocks.json`，不再拉 zip）；
- **启动落地**：`ApplyPendingComponentBlocks` 在没有任何进程占用组件目录的时刻替换，成功后清暂存 + 写 `Applied` + `Rescan`；失败（例如上一进程的输入法还赖着）只记日志并**保留 pending**，下次启动再试；
- 顺手补上历史遗留：`组件/<id>.old-<ts>` 残留此前注释说「启动再清」但实际没人清，现在启动时统一清。

## 四、实测（隔离实例，未碰用户正在用的主程序）

环境：`.jxai/tmp/voicetest/`，自编译 `jx.exe`（端口 18099）+ 假发布源（127.0.0.1:18098，提供 `releases/latest`、`blocks.json`、`voice-1.3.13.zip`），占用模拟=`voicetype/asr.log` 被持有且 cwd 落在 `组件/voice`（与真机 11-14 报错现场一致）。用户实例 `坚祥数字助理GO.exe` PID 400（13:06:03 启动）全程未动。

| 场景 | 结果 |
| --- | --- |
| A 未被占用 | 22:13 组件从 1.3.12 直接热更到 1.3.13，`applied.voice=1.3.13`（原有能力保留） |
| B **运行中（被占用）** | 22:17:12 一行安静日志 `组件 voice 1.3.13 已下载暂存，下次启动软件时自动更新（组件文件正被运行中的进程占用，关掉软件后会自动更新）`；`/api/status.update.componentsPending={voice:1.3.13}`，`lastError` 为空；本地 manifest **仍 1.3.12**、组件目录完整、无 `.old-` 残留；第 2、3 轮检查 `requests.log` 里 zip **只出现 1 次**（不重复下载） |
| C 重启（占用已撤销） | 22:22:08 `[更新] 组件 voice 已按暂存包更新到 1.3.13（启动时落地，无进程占用）`；暂存区清空、`componentsPending` 消失、`applied.voice=1.3.13` |
| D 启动时仍被占用 | 22:30:26 `[更新] 组件 voice 暂存包启动应用失败（保留，下次启动再试）: 旧组件目录挪不开: rename 组件\voice 组件\voice.old-…: The process cannot access the file…`；pending 保留、本地版本仍是 1.3.12、无半残目录 |

热更期间恰好在录音的行为：文件被占用 → 走暂存（不换目录、不杀 worker），**这一轮录音不受任何影响**，不会静默失败。

## 五、用户下次会怎样

1. **不需要手动杀进程、删目录**。运行中遇到新组件版本，包会在后台下好暂存，语音照常能用，设置页安静提示「重启软件后自动生效」；关软件再开就自动是新版。
2. **本次修复在主程序里**，要等下一次静默更新（engine 换好、重启生效）之后才具备这个能力；
3. **组件版本号没动**：本次没有改 `组件/voice/` 下任何文件，manifest 保持 1.3.12（未升 1.3.13，避免无内容变更的空版本）。
