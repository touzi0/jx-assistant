# 排查报告：子对话派生慢 + 归档后「列表里没有、实体还在、还能对话」

- 日期：2026-11-16（事故时间 2026-11-15 23:28）
- 现象：人工新建子对话时以为系统卡住，在子对话下拉里看到一条"没有内容"的会话，删掉（移入回收站）后，它从列表里消失，但稍后还能跟它正常对话，且再也找不到入口。
- 本轮**只做只读排查**：未改任何代码、未动用户主程序的库（只读 `mode=ro` 打开）、未启停用户正在用的实例。所有写操作与复现都在隔离实例里做（`jxprobe.exe`，独立 dataDir + 端口 19183，截至今已停止）。

---

## 0. 结论先行（TL;DR）

1. **派生慢的原因只有一个**：`copyInheritedContext` 把父会话历史**逐行、每行一个独立事务**写进子会话（`AppendRow`）。SQLite（WAL + `synchronous=FULL`）每行一次 fsync，实测 **3.13 ms/行 × 4435 行 ≈ 13.9 s**，占整个派生耗时的 **96% 以上**。读库只要 151 ms，广播/通知 0 ms。
2. **复制量的大头是"模型根本看不到"的东西**：复制了 27.7 MB，其中 **24.28 MB（87.8%）是 `kind=prompt` 的系统提示词/工具定义快照行**——`buildContext` 组装请求时会整类跳过（`context.go:189`，另有 647/754/1387/1485 同口径）。模型真正能看到的只有 **1.12 MB（4.1%）**：1 条压缩摘要（5.8 KB）+ 摘要边界之后的 1004 行原文。
3. **这次的"孤儿"不是删除造成的，是"归档 + mode 过滤"造成的**：从长期助理克隆出来的子对话继承了 `mode='assistant'`（`sessioncreate.go:159`），一旦 `archived=1`，
   - 右栏子对话下拉过滤掉它（`web/app-right.js:286`）；
   - 左栏回收站**无条件排除 mode=assistant**（`web/app-left.js:724`，同口径还有 651/686）；
   - 左栏搜索的服务端范围也排除它（`server.go:820` `searchableSessionsBaseSQL`）。
   → UI 上**零入口**，但右栏 `saveSession` 记着它、`restoreSession` 不检查 archived，所以"还能对话"。
4. **删与建确实撞车，但撞的是另一件事**：`sessions` 行在 **0.04 s** 就落库并出现在列表里，消息却在 **12.6 s** 后才写完，两者不在一个事务。这个 12.6 s 窗口里：
   - 下拉里能看到一个**正文为空的半成品**（前端把继承段折叠成一条「来自主对话 · N 条」+ 空态文案，看着就是"没有内容"→ 与用户描述一致）；
   - 此时「移入回收站」立即成功，创建流程照旧跑完并自动打开它 → 落成"有消息、能对话、但列表里没有"；
   - 此时「彻底删除」（硬删）会让复制过程外键失败，POST 返回 500，创建回滚、**不留孤儿**（全库孤儿 messages = 0，已核）。
5. 库里**共 4 条**这种"归档的 assistant 子对话"，本次两条在内（并不只是这一次）。找回方式：`PATCH /api/sessions/{id} {"archived":false}` 一条即可，恢复后立即回到右栏下拉。

## 一、派生/新建子对话为什么慢、慢在哪

### 1.1 调用链与代码位置

| 步骤 | 位置 | 说明 |
|---|---|---|
| 前端发起 | `web/app-right.js:519` `newAuxChat()` | `POST /api/sessions {parent, inheritContext:true}`；**无并发保护**，连点会并发建多个 |
| 建会话 | `server.go:1902` `handleCreateSession` → `sessioncreate.go:186` `Store.Create(m)` | **sessions 行此刻落库**（0.04 s 后列表即可见） |

| 复制历史 | `sessioncreate.go:193-194` → `context.go:486` `copyInheritedContext` | 慢的就是这里 |
| 逐行写库 | `context.go:514-545` → `store.go:988` `AppendRow` → `store.go:1061` `appendRowLocked` → `store.go:1083` `Exec(INSERT INTO messages …)` | 每行一次独立提交（无 begin/commit 包裹），且 `store.go:1092` 按 `touchesActivity`（`:1048`）每行可能再 UPDATE 一次 sessions |

### 1.2 实测（隔离实例，同机同盘）

口径：把用户真实主对话 `3d6e0b2b9169e2eeb7` 的 **6179 行 / 31.3 MB** 复制进探针库作父会话，然后连续做 3 次 `POST /api/sessions {parent, inheritContext:true}`。

| 阶段 | 实测 | 占派生总耗时 |
|---|---|---|
| **端到端 POST** | **12.62 / 12.63 / 12.73 s**（三次） | 100% |
| └ 其中：sessions 行落库、列表可见 | **0.04 s** | 0.3% |
| └ 其中：读库 `RawMessagesAll`（4435 行 / 27.7 MB） | **151 ms** | 1.2% |
| └ 其中：逐行写入 4435 行（每行一提交） | **13.89 s**（等价模拟，与端到端吻合）= **3.13 ms/行** | **≈96%** |
| └ 同 SQL 改**单事务**写入 4435 行 | **362 ms** | 参考（≈38×） |
| └ 序列化 | 0（Go 侧直接行拷贝，不经过 JSON） | 0 |
| └ 广播/通知 | **0**（HTTP 建子对话路径不发任何广播，前端在响应返回后才 `refreshDrawer()`+`loadSessions()`） | 0 |
| 对照：建**不带继承**的子会话 | **19 ms** | — |
| 对照：建顶层空会话 | **4 ms** | — |
| 派生后前端打开子对话 `GET /sessions/{id}?tail=200` | **411 ms / 683 KB** | 二次开销（真实库更大更慢） |

复制的消息条数/字节占比：**4435 行 / 27.67 MB = 派生过程的 100% 工作量**；其余（1 行 sessions、7 行 uploads、1 个 mkdir）合计 <1 ms。

### 1.3 复制了什么（按 kind 拆）

父会话（6179 行）复制时**排除 `kind=request` / `kind=audit`**（这两类共 1744 行没复制），其余全抄：

| kind | 行数 | 字节 | 给谁用 | 模型可见？ |
|---|---|---|---|---|
| `prompt` | 871 | **24.28 MB（87.8%）** | **只给前端**（「上下文材料/系统提示词/工具定义变更行」的审计展示） | ❌ `buildContext` 整类跳过 |
| `chat` | 3006 | 1.97 MB + 0.45 MB tool_calls | 模型 + 前端 | ✅（摘要边界之后的部分） |
| `aiuser` | 493 | 0.81 MB | 模型 + 前端 | ✅ |
| `env` | 41 | 0.15 MB | 模型（差分渲染）+ 前端 | ✅（部分） |
| `summary` | 1 | 5.8 KB | 模型（压缩摘要） | ✅ |
| `report` | 23 | <10 KB | 前端通知 | ❌ |
| **合计** | **4435** | **27.67 MB** | | **可见仅 1.12 MB（4.1%）** |

模型真正看到的：**摘要 5.8 KB（覆盖到 seq 5598）+ 边界后 1004 行 / 1.12 MB**。

另外：
- **不复制**的：系统提示词本身（子会话按自己的 mode **重建**，`a.systemPrompt(sess)`）、工具定义（`toolsFor(mode)` 现取）、checkpoints（文件版本快照）、deliveries、sessdata、组件/插件会话级覆盖、MCP 连接状态。
- **复制**的：所有行的 `thinking` 字段、`seq` 重排、摘要的 `CoversUpTo` 重映射（`context.go:523` 附近）、首行 `kind=inherit` 标记（前端靠它折叠继承段）。

> 结论：慢与"复制得对"无关，纯粹是**每行一次 fsync**；浪费的是 24 MB 的 prompt 快照与边界前的死数据。

## 二、删除与创建撞车时发生了什么

### 2.1 两条"删除"路径

| 路径 | 实现 | 效果 |
|---|---|---|
| 「移入回收站」（用户这次点的） | `web/app-right.js:379-385` → `PATCH /api/sessions/{id} {archived:true}` → `server.go:2314/2326` `SaveMeta` | **软删**：只改 `sessions.archived=1`，消息全留，会话照常运行 |
| 「彻底删除」 | `web/app-left.js:985` / 回收站清空 → `DELETE /api/sessions/{id}` → `server.go:2395` `handleDeleteSession` → `store.go:868` `Store.Delete` | **硬删**：事务内删 messages / sessions / uploads / sessdata / pending jobs。`messages.session_id REFERENCES sessions(id) ON DELETE CASCADE`（`store.go:123`）+ DSN `foreign_keys(1)` |

运行时/内存侧：内存缓存 `AppendRow` 失败会错行重排自愈；右栏下拉与左栏列表**都没有服务端缓存**，全部直查库——所以"列表看不到"一定来自**前端过滤**，不是索引/缓存不一致。

### 2.2 建会话的三个时刻（关键时间窗口）

| 时刻 | 动作 |
|---|---|
| t=0.00 s | `handleCreateSession` 进入 |
| **t=0.04 s** | `Store.Create` 提交 → **sessions 行落库、`GET /api/sessions?parent=` 立刻返回它**（未就绪） |
| t=0.04–12.6 s | 逐行复制历史（前半段还会先写一条 `inherit` 标记行） |
| **t=12.6 s** | 复制完成 → POST 返回 200 → 前端 `openSubSession(s.id)` + `refreshDrawer()` + `loadSessions()`（`web/app-right.js:534-535`） |

**窗口 = 12.6 s**。列表接口不做任何"就绪"过滤，所以窗口内任何一次 `refreshDrawer()` 都能看到这个半成品。

### 2.3 复现（隔离实例，三次）

| 场景 | 操作 | 结果 |
|---|---|---|
| A 纯计时 | 0.00 s 发起 | 0.04 s 列表可见半成品；12.73 s 完成；复制 4435 行 |
| B **创建中「移入回收站」** | 0.15 s PATCH archived=true | PATCH 200；创建照旧跑完（12.63 s，POST 200）；库 `archived=1`、4435 行全在；`GET /sessions/{id}` 200；`POST /sessions/{id}/chat` **照常跑完整模型轮**（审计行记录到模型调用）→ **用户现象 100% 复现** |
| C **创建中「彻底删除」** | 0.19 s DELETE | 复制时外键失败：`POST 500 {"error":"继承父对话上下文失败: constraint failed: FOREIGN KEY constraint failed (787)"}`；会话不存在、无残留 → **不留孤儿**（但前端会弹 `alert('新建子对话失败：…English…')`，`web/app-right.js:539`） |
| D 打开半成品 | 创建过程每 1 s 取一次 `?tail=50` | 0.19 s 只有 10 条、1.2 s 起 50 条——继承段**还没写完**；前端把已到的继承段折成一条「来自主对话 · N 条（含系统提示词）」，正文 0 条 → 显示空态文案（`web/app-chat.js:3003-3045`）→ **"看起来没有内容"** |

结论：撞车不会产生"库里实体 + 无入口"的孤儿；**产生无入口的是 B 场景的归档 + 前端过滤**（见 2.4）。C 场景是另一个真 bug（英文 500 报错 + 创建失败），顺带要修。

### 2.4 为什么"列表里没有入口"= mode 过滤，不是孤儿

子对话克隆父会话的 `mode`（`sessioncreate.go:159`）。长期助理主对话 `mode='assistant'`，所以**人工建的子对话也是 `mode='assistant'`**。归档后：

| 入口 | 过滤条件 | 结果 |
|---|---|---|
| 右栏「子对话」下拉 | `web/app-right.js:286` `.filter((s) => !s.archived)` | ❌ 被滤掉 |
| 左栏回收站 | `web/app-left.js:724` `s.mode !== 'assistant' && …` | ❌ 被滤掉（该条件本意是隐藏长期助理主对话本体，但它连带滤掉了所有 assistant 子对话；`collectEmptyTargets` `:686`、`deleteWorkspace` `:651` 同口径） |
| 左栏搜索（标题/内容） | `server.go:820` `mode != 'assistant' AND parent_id = ''` | ❌ 搜不到 |
| 右栏 localStorage 记忆 | `rpRegister('subs').saveSession` 存 `subState.cur.id`，`restoreSession(saved)` 不检查 archived | ✅ **这就是"刷新后还能对话"的来源** |
| API | 见 2.5 | ✅ |

## 三、改进方案：派生只带必要上下文（方案，未实施）

### 3.1 现状清单：哪些给模型、哪些只给前端

| 复制内容 | 给模型 | 只给前端 | 备注 |

| 边界前原文（被摘要覆盖） | ❌（`buildContext` 跳过 ≤boundary） | ✅（上翻历史） | 本次约占 1.9 MB |
| 已折叠（`compact=omit`）行 | ❌ | ✅（折叠视图） | |
| `prompt` 快照（系统提示词/工具定义） | ❌ | ✅ | **24.28 MB，纯审计展示** |
| `env` 快照（41 条） | 部分（差分渲染） | ✅ | 子会话自己会写新 env 行 |
| `report` | ❌ | ✅ 通知 | |
| `thinking` 字段 | ✅（回传 reasoning） | ✅ | 跟随所属行 |

| uploads 登记 | ✅（附件可读） | ✅ | 7 行，保留 |
| checkpoints / deliveries / sessdata | — | — | **没复制** |

### 3.2 只带「工具定义 + 系统提示词 + 压缩摘要 + 最近未压缩原文」会缺什么

- **系统提示词与工具定义本来就没复制**（子会话按自己的 mode 重建）——这块现在就是对的，无需改；真正要砍的是 `prompt` 快照行与边界前原文。
- **模型侧零损失**：`buildContext` 组装请求时会跳过 `prompt/request/audit/inherit` 与 `seq ≤ boundary` 的行，因此**少复制这些行，发给模型的请求逐字节不变**，前缀缓存命中率不受影响（这是本方案最大的卖点：省 88% 字节、语义无损）。
- **会丢的能力：历史查询**。`read_session_messages` / `search_sessions` 读的是"本会话"的行，不复制旧原文后，子会话里翻不到父会话早期内容（场景：子任务需要引用很早以前的那条结论 / 那条 SQL / 那个决定）。
  - 解法（不新增工具）：`inherit` 锚点行里写明「承接自 <父标题>（session_id=xxx，共 N 条）」，模型据此可直接 `read_session_messages(session_id=父id)` 翻旧账——该工具本来就接受任意 session_id。需要提示词里补一句"引用早期结论时用父会话 id 回查"。
- **文件路径/附件复用**：路径多落在摘要与最近原文里，通常够；uploads 照旧复制；checkpoints 本来就没复制，不受影响。
- **风险点：压缩边界一致性**。摘要行必须原样搬 + `CoversUpTo` 重映射（现有 `context.go` 已在做），否则 `buildContext` 的边界判断会错位、把旧原文误当有效上下文。

### 3.3 前端展示怎么办

- 现在：继承段被折成一条「来自主对话 · N 条（含系统提示词）」（`web/app-chat.js:1048` `inheritBlock`），空态文案已有（`:3043`）。所以"只复制一部分"在视觉上**几乎无差别**。
- 建议：折叠条改成 **「承接自：<父标题> · 最近 N 条 / 更早 M 条（点击加载）」**，点击按需从父会话分页拉旧消息（新只读接口 `GET /api/sessions/{id}/inherit?before=<seq>&limit=200`），拼进同一折叠区，分组渲染沿用现有 `groupTurns(inhTurns)` 基线。
- 不需要改空态文案；不需要改消息渲染主线。

### 3.4 改动点与预计提速

**最小可用版（只提速，不动语义）**

| 改动 | 文件 / 函数 | 规模 |
|---|---|---|
