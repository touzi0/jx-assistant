# 排查报告-20261118-右栏浏览器点超链接闪退

## 问题

用户报告（文件上传bug.doc）：桌面版右栏浏览器打开页面后，点击超链接整个程序闪退——「内部文件点击超链接跳转」「百度搜索后点击页面跳转」两个场景均复现，闪退时窗口残留在全黑+顶部花屏状态。

## 复现与实证

独立开发实例（独立数据目录 + `JX_DESKTOP_MUTEX` 互斥体隔离）复现成功：

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 点击 `target="_blank"` 链接（测试页红按钮） | **整进程崩溃** | 原地导航，进程存活 |
| 百度搜索结果页点击结果链接 | 必崩（结果链接全为 `_blank`） | 原地跳转 wimyhlo.com，进程存活 |
| 普通同窗口链接（测试页蓝按钮） | 正常（回归通过） | 正常 |

崩溃现场 Go runtime dump（决定性证据）：

```
Exception 0xc0000005 0x1 ...          ← 写访问冲突，整进程死亡
main.(*browserPanel).onNewWindow(...)       browser_panel_windows.go:806  ← putHandled.Call
main.(*browserPanel).createOnUI.func3(...)  browser_panel_windows.go:483  ← NewWindowRequested 回调
```

## 根因

点击 `target="_blank"` 链接触发 WebView2 的 `NewWindowRequested` 事件。右栏面板的处理器
`onNewWindow` 按 0.9.x SDK 头文件顺序排布的 `nwrArgsVtbl`（get_Uri=槽3、put_Handled=槽5）
调用 args 的 COM 槽位——**新版运行时（Chrome 157 WebView2）该接口的实际槽位布局已变**：
get_Uri 碰巧仍在槽3（所以 URI 能正确取出），put_Handled 槽5 实际指向别的函数，
调用即写访问冲突。COM 槽位调错是硬件异常，Go 的 `panelRecover`（defer/recover）兜不住，
整进程无声闪退，与截图的「全黑+花屏」现场吻合。

这与 `desktop_navguard_windows.go` 头注释的两个既有结论完全互证：

1. NavigationStarting args 同样实测发现新版运行时槽位重排（put_Cancel 槽7→槽8），
   「盲按头文件排布会把 get_RequestHeaders 当 put_Cancel 调——写访问冲突整进程崩溃」；
2. 该注释早已标注「右栏面板的 nwrArgsVtbl 潜伏错位问题另行修复」——即本问题在被
   修复前一直是已知潜伏雷，任何 `_blank` 点击都会引爆。

## 修复（browser_panel_windows.go）

不逐槽重测 NWR args（实证成本是整进程崩溃，不可控），**整体移除原生
NewWindowRequested 处理器**，改用 `AddScriptToExecuteOnDocumentCreated` 注入
`blankInterceptorJS` 在页面层把新窗口语义收敛为原地导航：

- `<a target=_blank/命名窗>` 左键点击（含 Ctrl/Shift）与中键（auxclick）→ preventDefault + 原地跳转；
- `<form target=_blank>` 提交 → 临时改 `_self` 后 requestSubmit（保留校验）；
- `window.open(url)` → 覆写为原地跳转（返回 null）。

安全性依据：脚本注入槽位位于主接口 vtbl 的 navigate 与 CallDevToolsProtocolMethod
之间——这两个槽位经日常工具链路（API 导航、CDP 点击/截图）长期实证无错位，注入安全。
漏网的浏览器内部路径走 WebView2 默认弹窗兜底（不崩，至多偶尔弹独立小窗）。

连带清理：`nwrArgsVtbl` 镜像、`onNewWindow`、struct/panelParts/detach/closeControllerOnUI
里的 newWin 全链删除；测试文件同步更新；`desktop_navguard_windows.go` 头注释的
「另行修复」措辞改为已修复事实。

## 验证

- `go build` 通过；`go test -run "TestPanel|TestClose"` 通过；
- 独立实例实测：上表三项全过，target=_blank 链接与百度结果页点击均原地导航、进程稳定。

## 遗留风险盘点与处置决定（2026-11-18 用户确认）

修复后对全仓库做了同款模式排查（args 类 COM vtbl 按老 SDK 头文件序盲排、未逐槽实测的镜像），发现两处同款潜伏雷，经确认**均不排雷、留观**：

1. **`pfArgsVtbl`（desktop_windows.go，ProcessFailed args 自愈通道）**：仅 `get_ProcessFailedKind`（槽3）一个取值调用。旁证：2026-11-17 前端出现卡死（渲染进程无响应类事件），后端进程未闪退——自救链路天然实测通过；且该槽位与本次实证「get_Uri 槽3 未挪」同位。触发场景为浏览器内核自身故障（用户操作不可达），即便槽位未来错位，代价也是「内核已坏时的二次闪退」，可接受。
2. **拖拽桥镜像（dropbridge_windows.go，WebMessageReceived args/2/Coll/File）**：日常拖文件即变相实证，持续未崩；`get_AdditionalObjects` 位于 v2 追加段，若未来运行时升级重排此处，症状是「拖文件闪退」，届时按本报告同款方法排查。

另：`stackguard_windows.go` 的 Go 回调栈缺陷护栏为上游缺陷（golang/go#69926）的临时缓解，删除条件见该文件头注释，与本报告无关。排查重启条件：WebView2 运行时大版本升级后出现「某类操作整进程无声闪退」——先查 args vtbl 槽位。

## 两颗潜伏雷的实测复核（2026-11-18 15:00–15:10，隔离实例）

用户要求对上述两处留观项做隔离实测。方法：`jx-dev2.exe` 独立实例（独立数据目录 +
`JX_DESKTOP_MUTEX` 互斥体隔离，与正在运行的正式版零冲突）。

### 雷一 ProcessFailed 自救通道：实测通过，风险关闭

强杀 WebView2 渲染子进程（模拟前端崩溃的最坏情况），日志 15:03:16 实录：

```
[ProcessFailed] 渲染进程退出           ← get_ProcessFailedKind（槽3）拨通，类型读取正确
[ProcessFailed] 渲染进程死亡：重新加载界面 ← 分级处置正确走 reload 分支
GET / ...                             ← 前端 1 秒内自动重载，进程全程存活，后端 HTTP 200
```

`pfArgsVtbl` 唯一的取值调用（槽3）实测正确，自愈链路真实工作——2026-11-17
「前端卡死、后端无恙」的现场正是这套机制在兜底。**不是雷。**

### 雷二 拖拽桥：维持留观，实际风险≈0（三层证据）

1. **触发窗口极窄（代码实证）**：drop 监听只挂主界面 composer（底部输入卡片）；
   仅桌面壳 WebView2 内激活（浏览器/手机/远程无 `chrome.webview`，函数直接
   return）；右栏浏览器面板**未挂桥**。用户猜测「拖到右侧栏才出问题」方向相反——
   右栏拖文件完全不走桥，只有桌面壳输入卡片才走。
2. **用户日常从未走过桥（日志实证）**：正式版 `data/desktop.log`（2.85MB 全量）
   零条「[拖拽桥] 收到」，仅三次「已挂处理器」。「拖了很多次没崩」并未实证到该
   号码链——拖的从未落在桌面壳输入卡片上。
3. **结构天然更安全（代码实证）**：拖拽桥全部调用走「头 3 槽（QI/AddRef/Release，
   COM 规范保证任何接口永不重排）+ QueryInterface 现场取独立小接口」模式，
   不存在 NWR 那种「大表中间槽位按老说明书盲排」的暴露面。

合成鼠标拖拽模拟 2 次未触发 drop（落点被前台窗口遮挡；用户在场使用电脑，
不宜继续真实桌面模拟，停止）。观察手段：`desktop.log` 出现「[拖拽桥] 收到」
而进程存活即天然实证；若出现「收到」且闪退，按本报告 NWR 同款方法排查。
