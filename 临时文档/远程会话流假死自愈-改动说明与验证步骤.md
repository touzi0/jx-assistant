# 远程/手机端「会话流假死」自愈 —— 改动说明与验证步骤

> 2026-11-15。用户主诉：远程网页（手机端尤其明显）在一个对话里待着，息屏或切后台
> 再回来，这个对话就不再刷新新消息，必须退出重进或整页刷新才恢复。
> 根因已查清：`/api/events` 有前端垫片（断了 3 秒自动重连）、会话流
> `/api/sessions/{id}/stream` 断了也有 `reloadMessages` 兜底——但手机切后台时连接是
> **假死**：读流挂在一次永不到达的 `read()` 上，既不报错也不结束，重连逻辑永远等不到
> 触发，界面就停在旧内容上。
>
> 本轮只动远程网页前端（`web/app-chat.js`）与验证脚本，**不发布、不动服务器**。

## 一、改了什么（只改 `web/app-chat.js`）

### 1. 判活：记录「最后一次收到会话流数据」的时刻

- `consumeStream` 每读到一段字节就刷一次 `view._lastDataAt`（含服务端每 15 秒必发的
  `: ping` 注释帧，见 `server.go` 的 `serveRun`）；每条新流开始时由
  `setStreamUI(true)` 也刷一次，静默从那一刻起算。
- 判死口径：`25 秒`（`STREAM_SILENT_MS`）收不到任何字节。正常生成中 delta 持续、
  空闲执行也有 15 秒一个 ping，所以 25 秒全静默＝这条流已经死了，不会误伤。
- 顺手补一道防串台：`consumeStream(res, view, sid, abort)` 收下这条流自己的取消器，
  界面已经放弃它（看门狗重建/切走）时，字节**只读不落地**——假死的连接事后若醒来，
  不会把同一批内容往界面上写第二遍。为此 `send / retryRun / resendEdit` 改为把
  **自己那条流的** abort 传给 `endTurn`（原先在收尾时读 `view.state.abort`，流被换掉
  后会认错自己的那条流）。

### 2. 看门狗：静默 25 秒就捅死重开

- `streamWatchdogTick`（每 5 秒）：仅当「该视图正在跑（`state.streaming` 且有待办会话）
  \+ 真的静默超过 25 秒」才动手；空闲会话、正常生成中的会话一律不碰。
- 页面在后台（`document.hidden`）时整轮跳过：后台定时器被系统压制、网络也可能被挂起，
  那种「静默」不代表流死了，交给回前台的那一次体检统一处理（不在后台空转重连）。
- `reviveSessionStream(view, why)`：掐掉这条死的读取（`detachStream`，后端执行照旧跑）
  → 探一次后端 → 还在跑就 `attachRun` 接回、已跑完就补拉一次把结果落出来。

### 3. 回前台/网络恢复立刻体检

- `visibilitychange`（变可见）、`pageshow`（bfcache 恢复）、`online`（网络恢复）三个
  转折点各调一次 `resumeStreamCheck`：
  - 有流在跑 → 用上面那个时间戳判健康，不健康立刻重建；
  - 没有本地流 → 探一次后端，**只有确实还在跑**才接回执行流；
  - 空闲会话 → 只多一次 `GET /api/sessions/{id}` 探测，不建流、不重连。

### 4. 节流：同一会话 5 秒内最多重建一次

- `streamReviveAt` 按**会话 id** 记上次重建时间（主对话/右栏子对话共用），
  `STREAM_REVIVE_GAP_MS = 5000`。抖动（连续多个 online/visibility 事件）里只重建一次。

### 5. 重建只补增量、不动视口、不整页重载

- `reloadMessages(view, { sinceSeq })`：带上界面已有的**最后一条消息序号**，只把这条
  之后的新消息**追加**进列表（历史一条不重取，DOM 前缀照旧复用）。
  服务端详情接口只支持 `tail / before_seq`（没有 after_seq），所以请求仍是那个基础窗，
  但「要哪一段」由序号判定：窗口起点盖住断点就追加，盖不住（断流期间新增超过一个窗口）
  才退回整窗对齐，宁可多取一次也不让中间缺条。
- 滚动位置沿用既有机制：`renderMessages` 里 `anchorSave/anchorRestore`（钉住阅读时按
  视口中线锚点补差）+ `followScroll`（贴底才跟随到底）。`reviveSessionStream` 全程
  不整页 reload、不 `jump`、不复位 `_pinned`。

## 二、验证（隔离实例 + 浏览器驱动，编译产物在 `D:\智能体工作区\数字助理GO`）

### 环境

| 角色 | 位置 |
|---|---|
| 编译产物 | `D:\智能体工作区\数字助理GO\stream-revive-20261115\jx-streamrevive.exe`（`go build` 通过，64,172,032 字节） |
| 隔离实例 | 端口 8850，数据/工作区全在 `.jxai/tmp/streamrevive/`（独立 config.json、data、ws），基址 `http://127.0.0.1:8851`（经代理） |
| 「假死」注入代理 | `.jxai/tmp/streamrevive/holdproxy.mjs`（8851 → 8850）：`hold=1` 时对会话流（`/chat`、`/stream`、`/retry`、`/edit`）**只回响应头、body 一字节不转发、连接不结束**——就是手机后台里那条假死的流；`blackout=1` 直接断连；每个请求带时间戳记 `proxy.log` |
| 慢速假模型 | `.jxai/tmp/streamrevive/slowmodel.mjs`（8852）：OpenAI 兼容 SSE，先吐一小段、再**静默 44 秒**、最后吐收尾正文——让「后端确实在跑 + 界面流静默」同时成立 |

### ① 断网 → 恢复（online 事件）

做法：`hold=1` 后发一条消息（会话流从开始就是死的）→ 12 秒后链路恢复（`hold=0`）→
页面在静默刚过 25 秒阈值时派发 `online`。

实测（`silentAt=25119ms` 时派发）：

```
info [JX] 会话流重建：网络恢复（会话 269066b7a4710d9aa1，从消息序号 18 之后补拉）
msgs 18 → 22，streaming true → false，stop 按钮收起
domMsgs 6，末条正文＝新到达的助手输出；scrollTop 373（= 新高度 1198-825，贴底跟随）
window.__probe === 'no-reload'（没有整页重载）
```

### ② 页面隐藏 31 秒 → 再可见（息屏/切后台）

做法：模拟 `document.hidden=true` + 派发 `visibilitychange`（后台期连接假死），
31 秒后链路恢复、`hidden=false` + 派发 `visibilitychange`。

实测：

```
后台期间：重建日志 0 条，streaming 仍 true，msgs 停在 26（界面就是卡住的旧内容）、
          DOM 只剩「发送中」占位 → 看门狗按设计不在后台动手
回前台：  info [JX] 会话流重建：页面回到前台（会话 269066…，从消息序号 26 之后补拉）
          msgs 26 → 30，streaming false，末条正文为新输出，atBottom=true（本来就贴底 → 跟随到底）
          window.__probe === 'no-reload'
```

### ③ 会话**真的在跑**但流静默 40 秒（看门狗）

做法：切到慢速假模型（静默 44 秒）→ `hold=1` 发消息（流一开始就死）→ 9 秒后链路恢复，
但那条流仍是死的。后端侧确认在跑：`GET /api/sessions/{id}` → `running=true`、
会话 `status=running`。

实测：

```
info [JX] 会话流重建：静默 29 秒（界面仍是执行态）（会话 41e65218127ca82172，从消息序号 0 之后补拉）
接回后：streamText 恢复「慢速假模型开始处理…（半句）」、streaming 仍 true、停止按钮在
44 秒时收尾正文到达（走的就是接回后的那条流）：msgs 4 → 6，body 含「静默期结束」，
streaming false —— 全部无需任何手动操作，window.__probe === 'no-reload'
```

### ④ 空闲会话不会被无意义重连

做法：会话空闲（`streaming=false`）时连续派发 3 组 `online` / `pageshow` /
`visibilitychange`。

实测：代理日志 6 条请求全是轻量探测（`GET /api/sessions/{id}`、`/api/approvals`、
`/api/questions`、`/api/sessions`），**会话流请求 0 条**，页面重建日志 0 条。

### ⑤ 抖动不连环重连（5 秒节流）

做法：会话在跑时，2.4 秒内连续派发 6 次 `online`，每次都把「最后收数据时间」人为推到
60 秒前（模拟抖动里反反复复的假死）。

实测：`网络恢复` 重建日志**只有 1 条**（节流生效），代理日志对应 1 条
`GET /api/sessions/{id}/stream`。其后看门狗因我人为保留的「静默 66 秒」状态、在 5 秒
节流窗之后又重建 1 次——两次间隔 ≥5 秒，属节流设计内（真实场景接回后就有数据，不会
再触发）。

### ⑥ 重建不整页重载、滚动位置不丢

- 对照（内容不变，只走同一条「增量补拉 + 重渲染」路径）：视口漂移 **0px**
  （锚点 `data-key=41e652…:16` 前后 `top` 均 404，`scrollTop` 均 500）。
- 钉住阅读（`_pinned=true`、`scrollTop=500`，视口停在历史中段）+ 看门狗补拉（这一轮
  内容确有变化：「发送中」占位与流式气泡被真实消息替换、折叠段重新量高）：
  `pinned` 保持 true、**没有回到底部**（`atBottom=false`）；锚点相对视口位移 106px
  （折叠段自身高度重算的余波，是本项目既有渲染路径的行为，不是「被拽到底」）。
- 贴底场景（见 ②）：重建后 `scrollTop = scrollHeight - clientHeight`，跟随到底。

## 三、已知边界（如实记录）

1. **25 秒阈值**：服务端 ping 间隔 15 秒，取 25 秒（一倍余量）。要更灵敏可调小，但
   网络抖动大时会多几次无谓重建（有 5 秒节流兜底）。
2. **折叠段高度重算的余波**：钉住阅读时如果这一轮内容结构变化很大（占位气泡/流式
   气泡被真实消息替换），视口可能漂移一两行到一百像素——这是既有渲染路径
   （`scheduleFolds` 在渲染后重新量高）的行为，本轮没有改动它；要像素级稳定需要在
   量高之后补一次锚点补偿，可作为后续优化。
3. **后台不主动重建**是有意的：后台定时器被压制、系统可能挂起网络，那时「静默」不
   等于流死了；回前台的一次体检足以覆盖，避免手机在后台反复建连接打请求。
4. 验证用的假死注入代理/慢速假模型只是测试脚手架，留在 `.jxai/tmp/streamrevive/`
   （不入库、不影响产品）。
